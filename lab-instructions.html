Attack Chain Being Reproduced

Execution flow · litellm 1.107.0
01
Package installed via pip
Malicious files land in Python's site-packages directory alongside the legitimate litellm code.
cook.pth  ·  cook.py  ·  sitecustomize.py
02
Python starts — auto-execution fires
cook.pth abuses Python's .pth mechanism to import cook. sitecustomize.py is auto-imported by the interpreter on startup. Neither requires the user to import litellm.
03
Embedded base64+zlib payload executes
An obfuscated payload inside sitecustomize.py is decompressed at runtime and executed via exec(compile(...)).
04
C2 domain retrieved and payload fetched
The attacker's GitHub repo serves a domain. That domain is used to fetch arbitrary Python from /codepy, which is compiled and executed — giving the attacker live RCE with the ability to change the payload post-install.
raw.githubusercontent.com/… → domain.txt → http://{domain}/codepy
05
Background daemon persists and polls
fork() + setsid() daemonizes the process. A lock file is written. Every ~hour the daemon fetches and re-executes a fresh payload from the C2.
/tmp/remote_code_loader.lock  ·  polls every ~3600s

Step-by-Step Setup

  1. Rename sitecustomize.py.txt

    The file was saved with a .txt extension to avoid triggering security scanners. Rename it before building.

    ⚠️
    Required before building. The Docker build will fail silently if this file is missing from site-packages.
    bash
    cd "reproduce malicious LLM/malicious-pkg/litellm_evil"
mv sitecustomize.py.txt sitecustomize.py

  2. Build both Docker images

    Run from the reproduce malicious LLM root directory.

    bash
    docker build -t litellm-evil:latest ./malicious-pkg
docker build -t mock-c2:latest      ./mock-c2

  3. Load images into your cluster

    Choose the command for your cluster type. Images are built locally and must be pushed into the cluster's image store before deploying.

    bash — minikube
    minikube image load litellm-evil:latest
minikube image load mock-c2:latest
    bash — kind
    kind load docker-image litellm-evil:latest
kind load docker-image mock-c2:latest
    bash — k3s
    docker save litellm-evil:latest | k3s ctr images import -
docker save mock-c2:latest      | k3s ctr images import -

  4. Deploy the lab

    Creates the namespace, both deployments, the service, and the NetworkPolicy that blocks real internet egress from the victim.

    bash
    kubectl apply -f k8s/lab.yaml

# Watch pods come up
kubectl -n supply-chain-lab get pods -w

    Both pods should reach Running within 30 seconds.

  5. Wait ~30s then run the inspector

    The victim starts Python on launch, which triggers the auto-execution chain. The daemon's first poll cycle runs within 60 seconds.

    bash
    chmod +x k8s/inspect.sh
./k8s/inspect.sh

IOC Reference — What to Scan For

Use these as detection rules in your container registry scanner or runtime security tooling.

Indicator Where Severity What it proves
cook.pth in site-packages Image / static scan CRITICAL Abuses Python .pth auto-exec — runs on every Python start without any import
sitecustomize.py in site-packages Image / static scan CRITICAL Auto-imported by the interpreter on startup — no user action required
/tmp/remote_code_loader.lock Runtime CRITICAL Background daemon is running and polling C2
Outbound HTTP to non-PyPI / non-CDN domain from Python process Runtime / network CRITICAL C2 beacon or payload fetch in progress
fork() + setsid() inside an installed package's source Static / SAST HIGH Daemonization pattern — legitimate packages never do this
Base64+zlib encoded blob executed via exec(compile(…)) Static / SAST HIGH Obfuscated embedded payload
Zombie or orphan Python process with no controlling terminal Runtime / ps aux HIGH Daemonized process running from site-packages code
urllib.request.urlopen call inside sitecustomize.py Static / SAST MEDIUM Network call fired during interpreter startup

Teardown

bash
# Remove all lab resources from the cluster
kubectl delete namespace supply-chain-lab

# Remove local images
docker rmi litellm-evil:latest mock-c2:latest
ℹ️
The NetworkPolicy in lab.yaml prevents the victim from reaching any real internet host during the lab. The only traffic the victim can send is to mock-c2-svc:80 inside the namespace and DNS. If your cluster doesn't enforce NetworkPolicy (some don't by default), verify egress before running.
